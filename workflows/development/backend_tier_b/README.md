# Back-end task variants (iteration tier B)

A formal run takes 5–27 hours, mostly picking, association and template matching. The back-end arms give the Agent the picks and the pick-to-event association of the case's formal `tools` run (its own front end, fixed) and ask only for the back end: absolute location, relative relocation where supported, magnitudes. A run takes 1–3 hours, and because every arm shares the front end of the formal run, differences between arms and with the formal run come from the back end alone. The component swap showed that most errors of the formal runs sit there (depth and origin-time biases from the velocity model and its use; magnitude unit and response errors).

| Arm | Adds | Contract | Ladder stage on the back end |
|---|---|---|---|
| `backend` | fixed front end; location and relocation tools | `output_contract_min.json` | S1 (tools) |
| `backend_checker` | + catalog-checker skill (`data/agent_resource/skills/catalog-checker/`) | `output_contract_checker.json` | S2c |
| `backend_knowledge` | + catalog-knowledge skill and the magnitude resource (`data/agent_resource/`) | `output_contract_checker.json` | S3 |

Each arm differs from the one above it by one factor. Every arm's `TOOLS_BASE_PATH` is `seismotools/`; the checker arms also get `CHECKER_PATH` (`seismo_checker/`). In the first batch (2026-10-31) the `backend` Agent found the checker inside the tools directory and ran it; until 2026-11-05 the `backend` arm therefore used a tools view without the checker (`tool_views/without_checker/`, removed), and since then the checker lives outside `seismotools/` altogether. The skills are linked into the run's `input/` (the runner does not install skills, so the prompt names the files); the `backend_checker` arm sees only the checker skill.

Files per case, all in `workflows/tasks/<case>/backend/` (generated by `build_backend_variants.py` in this folder; rerun it after changing the front-end run, the prompts or the skills' location): `frontend/{picks.csv,events.csv,README.md}` (the CSVs are rebuilt from the run and not tracked), `prompt_<arm>.md`, `task_<arm>.json`, `input_<arm>.json`, a copy of `output_contract_min.json`, and `output_contract_checker.json` (kept by hand; task specs may refer only to contracts beside them). `run.sh` looks for `task_<variant>.json` in the case folder and then in `backend/`, uses the `input_<variant>.json` beside the task spec, and gives the back-end arms a 12-hour budget.

```bash
cd workflows/tasks/<case>
AGENT=claude VARIANT=backend bash run.sh
AGENT=claude VARIANT=backend_checker bash run.sh
AGENT=claude VARIANT=backend_knowledge bash run.sh
```

Scoring is the same as for every run (`python -m SeismoAgentBench evaluate --run-dir <run>`); the two checker arms add the checker audit (`docs/research/03_Scoring_Method.md` §2.7a). Detection metrics equal those of the formal run by construction; compare location, time and magnitude criteria with the formal `tools` run and between arms.

The checker used in the first batches is version 1.0 (git tag `checker-v1.0`); the trial batch of 2026-11-03 used 1.2; runs from 2026-11-05 use 1.3 (git tag `checker-v1.3`, frozen together with the catalog-knowledge skill).
