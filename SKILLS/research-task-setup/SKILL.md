# 一个任务怎样组织

## 0. 做事的顺序

0. **新建任务时先记录运行环境**：生成 `docs/environment.md`（见 §7），之后估算运行时间、决定在哪里跑都以它为准。
1. **先写 design**：目标、数据、执行逻辑和口径想清楚后再写代码；design 有改动时先改 design。
2. **再在 registry 登记**：把要做的步骤按 design 的顺序列出，写好完成标准，然后才动手。
3. **先端到端跑通，再逐步求精**：先用简单的做法把从数据到产出的整条流程跑通，看到结果的样子，再决定哪里值得做细。验证在每一步保持轻量（抽查几十条、检查关键计数），不要一开始就追求论文级的严谨。
4. **需要用户拍板的事情先问**：方案选择（如分类体系、模型参数化）、范围边界、启动代价高的批量运行、删除东西。用户的决定记进 results.md（写明日期），之后不再反复讨论。
5. **每完成一步就收尾**：改 registry 的状态，在 results.md 记关键数字，在 changelog.md 记一行。
6. **分层补充时先归档、后比对**：范围分几期扩大（先做最重要的一批，再逐层补充）时，每补一层前把当前结果整体复制到 `results/archive/before_<这一层>/`，补完后逐行比对前面各层的结果，确认只有预期的变化，并把变化记进 results.md。新的一层常会顺带改动旧结果（多数是更正，也可能是误改），不比对就发现不了。

## 1. 何时新开一个任务

下一步的工作与当前任务相比，在**目标、数据、验证方式、产出**这四项中有两三项不同，就新开任务，不在原任务里接着加。原任务的 design 往往已把这部分写在“不做的内容”里，硬加进去会推翻它的边界，design 和 registry 都会变得冗长、主线不清。

例：从“用元数据筛出相关文献，对照外部清单验证，产出一个浏览页面”走到“从全文中抽取结论，需要人工金标准，产出一篇文章”——四项里变了三项，应新开任务。

新任务和上游任务的接口：

- **固定输入的版本**：新任务只读上游的几份交接产出（清单、表、写回到数据层的字段），以符号链接放进自己的 `data/`，并在 design 里写明所用的版本（文件版本号或 git 提交）；上游以后再改，新任务自己决定是否跟进，输入不会被悄悄改变。
- **上游保留维护**：上游任务继续负责自己数据的扩充和修正，以及它已发布的产出。
- **共享产出的归属要定**：同一个页面、表或数据文件只由一个任务负责写。新任务先做自己的原型；成熟后再由上游读入新任务导出的结果，不让两个任务同时改同一个文件。

## 2. 文件树

每个任务（如一项研究或一个分析工具）是一个独立文件夹：

```
<task>/
  docs/       设计和记录：design.md、registry.md、results.md、changelog.md、environment.md（及 conda_env.yml），以及 archive/（旧版文档）
  data/       任务的输入数据，按数据类型和层级分文件夹；大数据只放符号链接
  scripts/    脚本，按设计的几个部分分文件夹
  results/    结果，与 scripts 同样分组；另有 _process/（中间过程）和 archive/（旧版本）
  logs/       运行日志，与 scripts 同样分组
  pages/      （可选）给读者看的网页，每个是单个 HTML 文件
```

- 结果和日志放在任务自己的文件夹里，不放到仓库顶层。
- 重跑代价高的中间过程（长时间计算的中间文件、大模型的原始输出等）放 `results/_process/`，保留但不作为最终结果；被取代的旧版本放 `results/archive/`。旧东西一律归档，不删除，确实要删时先问用户。
- 脚本只经由一个路径模块读取 `data/` 下的路径，不写死路径，也不绕过 `data/` 直接读共享存储；数据换位置时只改符号链接（和 `data/README.md`），脚本不动。

### data/ 的组织

`data/` 只放**输入**：外部获取的数据和上游任务的交接产出。本任务自己算出的东西放 `results/`，不放回 `data/`。

```
data/
  README.md           每一项的来源、版本、获取日期、大小，符号链接指向哪里
  <数据类型>/          如 waveforms/、catalogs/、stations/、models/
    raw/              原始数据，按获取时的样子保存，只读
    processed/        外部或上游已处理过的版本（格式转换、筛选、合并后的交接产出）
```

- **先按类型、再按层级**：同一类数据的原始版和处理版放在一起，一眼看出谁由谁而来；某类数据只有一层时可以不建层级子文件夹。层级的名字在任务内统一，不要一处叫 `raw/`、另一处叫 `original/`。
- **大数据只放符号链接**：单个文件或目录较大（约 100 MB 以上，或不适合进 git）时，数据本体留在共享存储，`data/` 下只放指向它的符号链接，用绝对路径。小数据（站点表、小目录、配置）可以直接放文件。
- **链接只读**：不通过链接改写共享数据；要修改就复制一份或生成新版本，结果写进 `results/`。
- **上游交接产出也用链接**：链接到上游任务的固定版本（带版本号的文件或目录），在 `data/README.md` 写明版本；跟进上游新版本时只改链接，并在 changelog 记一行。
- **git 只管链接本身**：符号链接和小文件进 git，大数据本体不进；链接目标所在的存储在 `data/README.md` 写清，换机器时照着重建链接。

## 3. docs 中的文档

| 文档 | 作用 | 写法要点 |
|---|---|---|
| `design.md` | 任务的总览设计，先于实现 | 聚焦研究目标、数据、执行逻辑、预期结果；用逻辑明确的流程图展示整体流程；章节少而精；不写任务编号、进度、改动历史和会随数据变化的结果数字 |
| `registry.md` | 按 design 做具体实现的预注册：每一步做什么、完成标准、状态、结果在哪里 | 按 design 的逻辑顺序组织，与 design 的部分和步骤一一对应；新工作先登记再动手；完成一项改一项状态 |
| `results.md` | 重要结果和做过的决定，便于检查核心数字 | 按 design 的顺序分节；只记结论性的数字，写明每个数字来自哪个文件；用户的决定写明日期 |
| `changelog.md` | 每次核心修订 | 按日期倒序，每条修订一行 |
| `environment.md` | 运行环境：本机 CPU、内存、磁盘、GPU、conda 环境，以及可访问的集群 | 新建任务时用脚本生成（见 §7）；集群一节手动补充；环境变化时重新生成 |

**design.md 建议的结构**：

- **目标**：要回答什么问题，产出哪几类结果。
- **数据**：用哪些数据、范围多大、数据本身的局限（例如覆盖不全时，统计量只是下限）。
- **检验基准**：用来检验结果的外部基准或已知答案怎么来、有什么局限。若任务含分类体系，写清每一层的定义、来源和完整性检验。
- **执行逻辑**：分几部分、每部分几步，配流程图；每步写清输入、由谁判断（规则、程序、模型、人）、得到什么。只写主线，方法细节指向下一节。
- **相关方法介绍**：集中写各步的方法细节。每个方法先用一张简洁的 mermaid 流程图给出步骤，再用表格或要点列规则、参数和例子；图和网页上的每一个视觉元素（点、线、颜色、位置）各表示什么，用一张“部分 / 表示什么”的表写清；再写“怎样读、不能怎样读”。不要写成大段文字：读者要能先看图抓住流程，再查表找细节。mermaid 写完先离线渲染一遍，确认没有语法错误。
- **口径、验证、产出、不做的内容**：各一节，写短。

**经验**：

- design 是先行的设计，registry 跟着它走。design 里一旦写满任务编号、状态和“某日起改为……”这类历史，就变成了日志，读者抓不到主线。编号和状态放 registry，历史放 changelog。
- 层级名称要一眼分出上下层。几个都表示“一类”的泛词并列（如 family 和 class）时，读者分不清谁包含谁；每层用只表达本层含义的词。名字尽早定，后期改名要同时改文档、图、网页和交付数据，代价很大。
- 流程图和阶段编号按真实的执行顺序排：一个步骤用到另一个步骤的产出，就必须排在它后面。
- 相邻两步的关系要在后一步的开头说明。只写两个抽象的步骤名，读者看不出两者的联系；在后一步开头写一句“上一步只说明了……，这一步回答……”，再给一个具体例子，关系就清楚了。步骤名也用直白的说法。
- 需要给不读中文的合作者看时，另写 `design_en.md`，内容一一对应，注明以中文版为准，术语与英文产出一致；改中文版时同步改英文版。

## 4. scripts、results、logs 的分组和命名

- **按设计的几个部分分组，不按小步骤分**：每个小步骤一个脚本、一个结果文件夹，很快就无法管理（曾有一个任务整理前近百个结果文件夹、五十多个脚本，按设计分成 3 个部分后是 20 个脚本）。
- **文件名带部分和步骤编号**：如 `a1_2_<动作>.py`，`a` 是部分代号，`1_2` 是第 1 步的第 2 个子步骤。只有一个步骤确实复杂时才拆子步骤，不要每个小任务写一个脚本。scripts、results、logs 三处用同样的分组和名字。
- **结果文件夹只放最终版本**：不带日期和 `_v2` 一类后缀，历史版本进 `archive/`，对应关系写在 `results/README.md`。
- **默认参数就是最终运行的参数**：每个脚本不加参数即复现最终结果，`--help` 能看全部参数。
- **共用代码放一个模块**：如 `scripts/common.py`。文件夹不要和模块同名（`common/` 与 `common.py` 并存会让 import 出错）。
- **改前备份**：在 git 仓库里，改脚本前先提交；git 不管的文件（大结果、本地数据）改前复制到 `logs/.../backups/`。大的整理前把 scripts 和 docs 整体打包存档。
- **每次运行用独立的输出目录**：准备批量作业的脚本若默认写进同一个目录，后一次会覆盖前一次的输入文件和编号对照表。默认目录带上运行名，目录已存在时拒绝写入。
- **测试脚本放进任务里**：浏览器测试、渲染检查这类脚本放在任务的 `scripts/` 下，不放临时目录；临时目录在会话重启时会被清空。

## 5. 若任务含大模型判定

- 判定结果和代码分开存放，每条记下模型、提示词版本和时间，之后靠它们区分来源、决定合并顺序。
- 原始输出和批次文件放 `results/_process/`。
- 依赖大模型判定的步骤在复现时不重跑，把已有判定作为输入读入；“默认参数复现最终结果”指的是这一点。
- 启动大规模批次前先问用户（费用和时间）。

## 6. 整理目录后怎样验证

每次移动或改名都按这个顺序验证，不跑长时间的试验：

1. 写一个可重复执行的整理脚本：先试运行，列出全部移动并检查目标是否已存在；确认后再执行，并保存移动清单。
2. 用同一个脚本改写所有引用路径（代码、README、文档），再搜索残留的旧路径。
3. 每个脚本跑 `--help`，检查所有默认输入路径都存在；用 `find data -xtype l` 检查没有失效的符号链接。
4. 移动前给结果留快照；用移动后的脚本把便宜、确定性的步骤重跑一遍，逐个文件和快照比对。会随运行变化的内容（时间戳、随机种子、matplotlib SVG 里的随机元素编号）比对前先去掉。

第 3 步最常抓到问题：整理脚本的正则漏匹配一批路径时，默认输入路径会指向不存在的位置。

## 7. 运行环境

**新建任务时记录到 `docs/environment.md`**：

1. 在任务所用的 conda 环境里（或给出环境名）运行本 skill 目录下的 `collect_env.sh`：
   ```
   bash <skill 目录>/collect_env.sh <conda 环境名> > docs/environment.md
   conda env export -n <conda 环境名> --no-builds > docs/conda_env.yml
   ```
   脚本记录主机、系统、CPU（本进程可用核数和总核数）、内存、磁盘、GPU（型号、显存、驱动和 CUDA 版本）、conda 环境；本机能用 Slurm 时一并记录分区概况和 FairShare。没有的命令自动跳过并注明，不会报错。
2. **集群一节由用户补充**：脚本只能看到本机。若还能访问其他集群（登录方式、分区、账户、每人限额、存储路径），提示用户按文件末尾的表填写；没有其他集群就写“无”。不要替用户猜测集群的信息。
3. 自动检测不到的限制手动注明，例如登录节点的每人内存和 CPU 限额（`free` 显示的是整台机器）。
4. 环境变化（换机器、升级环境、加了 GPU）时重新生成，先用 `diff` 看变化，保留手动补充的内容，并在 changelog 记一行。

**使用时**：

- 估算运行时间、决定并行度和在哪里跑时，以 `environment.md` 为准，不要按默认假设（例如假设有 GPU）。
- 作业日志记下每一步的开始时间和关键计数，便于事后核对。
- 在共享集群上，小的检查在登录节点做，重跑整条流程、读大矩阵、GPU 推理提交到调度系统；具体集群的限制和排队经验另见对应的集群 skill（如 `fasrc-slurm`）。
