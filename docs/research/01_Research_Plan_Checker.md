# 研究计划 B：把地震学知识和工具引入通用 Agent 的 checker（seismo checker）

**定位：** 主线工作，论文大纲见 [`paper/01_Outline.md`](../../paper/01_Outline.md)。如果效果不足以单独成文，退回 [研究计划 A：基准](./00_Research_Plan_Benchmark.md)。本计划要的是深度：在现有案例上把方法做扎实，不追求案例和模型的覆盖面。

## 1. 为什么需要高精度地震目录

地震目录是地震学大多数后续研究的输入，精度直接决定能得到什么结论：

- **断层成像：** 相对定位到百米级，才能看出断层面、分支和破裂的几何；
- **余震和震群的演化：** 完整性（Mc）和发震时刻决定能否看清迁移、前震、触发和流体扩散；
- **地震预测和危险性：** ETAS 一类模型和 b 值分析依赖完整、震级标度一致的目录；
- **诱发地震和火山监测：** 运营方的交通灯制度、火山活动的预警，需要在几天内得到可靠的深度和震级。

高精度目录目前要靠专家花数周反复调试：选速度模型、调关联参数、做模板匹配和双差定位、校正震级。这一过程难以复制，也难以在新序列发生时迅速完成。

## 2. 核心贡献

> **把地震学的知识和工具，通过一个不依赖参考目录的 checker，引入通用 Agent 的 harness，让 Agent 能检查并修复自己构建的目录，朝高精度目录靠近。**

具体是三件事：

1. **seismo checker：** 把专家诊断目录的经验写成确定性的检查，覆盖六个阶段（数据、拾取、关联、绝对定位、相对定位、震级）。它只报告症状（测了什么、超出预期多少），不给原因和修复，不用参考目录，不含任何案例的数值。
2. **知识 skill：** 专家在看数据之前就知道的东西：小批量先验证再全量、两个候选怎样取舍、"症状 → 可能原因 → 区分实验"手册，以及检查看不到的误差（速度模型和近地表、水平框架、模板匹配、震级定标）。
3. **接入方式：** 工具库、checker 和知识都只是放进 Agent 环境的文件，外加一条输出约定（提交 checker 报告，并对每个报警给出处置：已修复，或附证据说明理由）。不改 Agent 的循环，不加子 Agent，所以同样的做法适用于任何通用 harness。

## 3. 应用场景

- **新序列的快速目录：** 大震或震群发生后几天内给出接近研究级的目录，而不是等数周到数月；
- **临时台阵和节点台阵：** 布设密集但缺少分析人员的观测，Agent 承担常规处理；
- **历史数据重处理：** 用统一流程重新处理已有波形，得到一致的高精度目录；
- **诱发地震和火山监测：** 运营方或观测站持续产出目录，checker 报警提示需要人工复核的地方。

在这些场景里，专家的角色从"自己做每一步"变成"审核 Agent 的处置记录"：checker 报告和处置说明了哪里有问题、Agent 改了什么、为什么认为剩下的报警没问题。

## 4. 对相似工作的启示

这些经验来自目前的运行和离线检验，对其他科学领域引入领域工具的 Agent 也适用：

1. **只报症状，要求处置：** 确定性的症状报告加上"每个报警都要处置"的约定，比让模型自我批评更能防止它为错误找理由。
2. **正确的参考实现是有效的知识载体：** 震级单位错误被挡住，主要是因为 Agent 照用了 checker 和知识里正确的计算代码，而不是因为报警本身。
3. **检查值不是选择标准：** 让检查值变好看的改动常常是表面修复；手册要写明哪些改动不该做。
4. **分清能看到和看不到的误差：** 自身数据能看到的错误（实现错误、深度堆积）checker 可以挡住；所有台站或事件共有的偏差（速度模型、定标）看不到，只能靠知识和外部资料。
5. **修工具比教 Agent 可靠：** 定位程序的深度基准约定这类隐蔽错误，改工具的默认值比写进提示词有效。
6. **以 human-in-loop 结果为标尺：** 参考目录彼此不完全一致，应以同一数据上专家流程的结果作上限，并按步骤归因差距。

## 5. 实验需求

- **案例：** 现有六个案例足够，覆盖三个难度级别和诱发、震群、火山、大震、多断层五种情形。规则是在这六个案例上总结的，结果按"规则来源于该案例 / 不来源于该案例"分开报告，不另加案例。
- **Agent 框架：** 只用 Claude Code（当前模型 GLM-5.3）。贡献在于接入方式，不在于比较模型。
- **比较：**

| 实验 | 内容 | 回答的问题 |
|---|---|---|
| checker 本身 | human-in-loop 目录（应当干净）上的误报；误差已知的 Agent 目录上的检出；合成回归测试 | 报警可靠吗？ |
| 后端消融 | 拾取和关联固定，比较"只有工具 / + checker / + checker 和知识"，每次 1–3 小时 | checker 和知识在定位和震级上各起什么作用？ |
| 完整流程（主实验） | S1 `tools` 对 S3 `knowledge`，每个案例各两次；S2c `checker` 只在需要消融时运行 | 能弥合多少与专家的差距？ |
| 处置分析 | 报警数、真修复、表面修复、证据不足的理由 | Agent 怎样使用 checker？ |

- **主要指标：** 可信标准的不通过数，以及按维度的差距弥合率 (S3 − S1) / (最终 − S1)。

## 6. 现状（2026-11-05）

- **能挡住实现类错误：** 后端消融中，只有工具的变体在三个案例上犯了震级单位或响应错误（偏差约 −1.0 至 −1.4），带 checker 的变体都没有犯；深度堆积这类看得见的症状也被修好（[图](./assets/checker_effect/checker_effect_summary.png)）。
- **对速度模型类偏差没有帮助：** 时间和深度偏差没有一致改善，报警还诱导了把误差从深度挪到时间的改动。只有一次知识变体（正确使用已发表模型和基准面）把三项一起修好。
- **检测没有测过：** 后端消融的前端是固定的；知识中关于模板匹配的部分要靠完整流程检验。
- 当前冻结版本 `checker-v1.3`（含知识 skill），已通过无模型的端到端测试，还没有经过 Agent 运行。设计和版本见 [`04_Checker_Design.md`](./04_Checker_Design.md)，证据见 [`progress/expert_experience_evidence.md`](./progress/expert_experience_evidence.md)。

## 7. 风险

- **看不到的误差是边界：** 速度模型和近地表、震级定标水平、主震尾波中的漏检，只能靠知识；而知识能否用上，取决于有没有可用的区域资料。
- **表面修复：** 报警会诱导 Agent 改到检查通过为止。对策是手册写明哪些改动不该做，把只会诱导修改的检查降为只报告。
- **效果可能太小：** 如果 S3 相对 S1 的改善在重复运行的离散之内，就退回计划 A，把 checker 作为基准中的一个条件来报告。
