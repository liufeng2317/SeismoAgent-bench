# 知识 skill 重写方案

状态（2026-11-07）：方案，待审。本文写给研究者，说明为什么要重写给 Agent 的知识 skill、重写成什么样、怎么检验。checker 本身的设计见 [`02_Checker_Design.md`](02_Checker_Design.md)；开发循环的两轮结果见 [`progress/records/17_dev_round1.md`](progress/records/17_dev_round1.md) 和第二轮记录（待写）。

## 1. 为什么要重写

### 1.1 两轮开发暴露的问题

开发循环（主震前后一天，六个案例各一次）里，Agent 出错的地方大多不是"不知道"，而是"没按该有的步骤做"或"把规则用错了地方"：

| 现象 | 案例 | 性质 |
|---|---|---|
| 没做相对重定位，偏离构造 14 % | Ridgecrest 第二轮 | 漏步骤 |
| 没做模板匹配，召回 1.03 → 0.66（理由之一是 checker 会把没有拾取的检测事件算进"拾取过少"） | Magna 第二轮 | 漏步骤，checker 反向激励 |
| 为回应"台站没有拾取"补进噪声很大的单分量拾取，四分之一定位偏 5 km 以上 | Maple 第一轮 | 补救本身没检验 |
| 用残差否定了正确的 S−P 深度报警 | Magna 第一轮 | 规则自相矛盾 |
| 把 Vs 缩放到 Wadati Vp/Vs、以报警归零为采用标准，深度校正过头 | Magna 第二轮 | 规则没写适用边界 |
| 把能修的深度堆积说成"调参"，拒绝修正 | Kaikōura 第一轮 | 缺少具体做法 |
| 按 skill 的路径写法把产品交到 `work/work/` | Kīlauea、Ridgecrest 第一轮 | 说明有歧义 |

1.5 的逐条修补解决了其中三条（Maple 6 → 2 项不通过，Kaikōura 5 → 2），但同时让 Magna 学会了"以报警归零为标准"。逐条修补在一个地方堵上，另一个地方又冒出来。

### 1.2 前沿工作说明的问题

- **专家编写的领域 skill 有效，科学领域收益最大。** SkillsBench（87 个任务、18 种模型与框架组合）：精选 skill 使通过率 33.9 % → 50.5 %；自然科学类 42.0 % → 70.8 %；Agent 自己生成的 skill 反而低于不给（−8 到 −11.5 个百分点）。
- **专注的流程优于面面俱到的文档。** 同一研究：精简或中等长度的 skill 提高 19–21.5 个百分点，"全面文档式"只有 0.7；1–3 个模块最好，4 个以上降到 10.1。
- **skill 的作用主要是稳住动作。** 对 8,000 多条运行记录的分析：65.7 % 的有效用法是提供流程锚点，单纯注入知识只占 4.5 %。
- **skill 有害的情形：** 只规定一条"正确"流程而没有适用边界和退路；长时间运行中早先读到的内容影响减弱。
- **编写方法（Anthropic 指南）：** 先建评测，从不带 skill 的基线出发；复杂任务写成可勾选的流程清单；"校验 → 修复 → 再校验"的闭环；易错操作给现成脚本；示例具体；术语和规则一致；参考文件只引一层。
- **从运行记录提炼**（ACE、Trace2Skill）：每次小的增量修改，记录每条内容是否有用，避免整体重写丢失有效内容。

### 1.3 现在的 skill 差在哪里

现在的知识 skill 约 9,800 词，入口 `SKILL.md` 只是一张路由表和四条原则，主体是按症状组织的说明：症状 → 可能原因 → 区分实验 → 修法。这正是"全面文档式"的写法：

- **没有流程主线：** 哪些步骤必做、每步之后跑哪个 checker 阶段、什么情况下才能进入下一步，都没有写成清单。
- **没有脚本：** 加入新拾取前后的对比、改报期望震源、剔除台网外事件、交付前自检，都要 Agent 现写。
- **规则缺适用边界：** 写了"怎么做"，没写"什么时候不适用、不适用时怎么办"。
- **几乎没有具体例子：** 为防泄漏删掉了案例，连匿名化的例子也没有。
- **一致性差：** 内容是随着检验结果一条条补上的，出现过前后矛盾。

这些一部分来自当初有意的设计：checker skill 只讲用法以便和知识分开做消融；知识不写案例名、不给具体模型以防泄漏；内容来自离线检验的结论，自然写成"原因—证据"式。这些约束保留，改的是写法。

## 2. 设计原则

1. **流程为主，症状为辅。** 入口给出完整流程清单；症状手册保留为参考，按需查阅。
2. **每阶段一个闸门。** 每个阶段结束跑对应的 checker 阶段，按清单处理报警后才进入下一阶段（校验 → 修复 → 再校验）。checker 就是这个闭环里的校验器。
3. **默认做法 + 适用边界 + 退路。** 每条规则写成：什么时候适用；默认怎么做；什么时候不适用、那时怎么做；用什么证据判断（不是 checker 量本身归零）。
4. **易错操作给脚本。** 通用、不含案例信息的小脚本，参数有说明，默认值有依据。
5. **具体但匿名的例子。** 每条关键规则配一个例子，写数字、不写案例名和地名。
6. **精简。** 入口 `SKILL.md` 不超过 200 行；整个 skill 不超过三个模块（入口流程、阶段说明、参考）；删去 Agent 本来就知道的解释。
7. **约束不变：** 不出现案例名；不给具体区域的速度模型；checker 只报症状；不定制 Agent，只往环境里加文件。

## 3. 新结构

```
catalog-knowledge/
  SKILL.md                 流程清单：阶段、默认做法、checker 闸门、何时可以偏离（≤ 200 行）
  stages/                  每阶段一个文件：决策规则（适用 / 默认 / 不适用时 / 证据 / 例子）
    01_data_and_picks.md
    02_association.md
    03_absolute_location.md
    04_template_matching.md
    05_relative_relocation.md
    06_magnitude.md
    07_submission.md
  scripts/                 通用脚本（第 5 节）
  reference/               现有症状手册和 checker 看不到的误差，加目录，删重复
    symptoms_*.md
    not_visible.md
```

`SKILL.md` 只引用 `stages/`、`scripts/`、`reference/` 中的文件，不再层层嵌套。`catalog-checker` skill 保持只讲用法和交付要求，加一个交付前自检脚本（见第 5 节）。

## 4. 流程清单（`SKILL.md` 草案要点）

每个阶段写四项：默认做法、必须跑的 checker 阶段、通过条件、可以偏离的情况。草案：

| 阶段 | 默认做法 | checker 闸门 | 通过条件 | 可以偏离的情况 |
|---|---|---|---|---|
| 0 计划与试跑 | 读数据和台站；在一小批数据上试拾取、关联、定位，确认代码和参数 | `pilot.py`、`--stage data` | 小批量各阶段无报警或报警已解释 | — |
| 1 拾取 | 三分量台站用 PhaseNet；单分量台站只在检验通过后加入 | `--stage picks` | 每个没有拾取的台站有说明；新加入的一组拾取通过对比脚本 | 单分量台站的拾取离散明显大于三分量台站时不用 |
| 2 关联 | 按序列密度设关联参数，在试跑上调好 | `--stage association` | 报警已处理 | — |
| 3 绝对定位 | 速度模型按区域知识选（写明来源）；找不到时用通用模型并按 `reference/not_visible.md` 处理近地表；深度搜索从台站平均高程开始 | `--stage location` | 深度堆积已处理（无约束事件报期望震源）；S−P 深度报警超过门槛时方向已纠正；台网外事件已剔除 | 改模型时不以 checker 量归零为标准 |
| 4 模板匹配 | 序列类任务必做：用定位好的事件作模板，阈值取通过零假设检验的最低值，检测事件并入目录 | 并入后重跑 `--stage location` | 检测事件已并入并标明 | 只有在数据不支持时（例如模板太少）可以不做，须写明 |
| 5 相对重定位 | 事件密集时必做：互相关差分时 + hypoDD 或 GrowClust | `--stage relocation` | 整体平移、大幅移动、收缩无报警或已解释 | 事件稀疏、连接不足时可以不做，须写明 |
| 6 震级 | 用震级资源中的标准实现，单位和仪器响应先在少量事件上核对 | `--stage magnitude` | 复算一致 | — |
| 7 交付 | `--stage all` 跑最终产品；逐条处置报警，给证据；运行交付前自检脚本 | 交付自检 | 自检通过 | — |

清单写成 Agent 可以复制到自己记录里逐项勾选的形式。

## 5. 脚本

都放在 `catalog-knowledge/scripts/`（交付自检放在 `catalog-checker/scripts/`），只用输出约定里的文件格式，不含任何案例信息。

| 脚本 | 作用 | 输入 | 输出 |
|---|---|---|---|
| `compare_pick_groups.py` | 加入一组新拾取（新拾取器或新台站）前后对比：这组拾取的残差离散与原有台站比；加入前后定位的变化 | 两次定位的目录和拾取（含 `residual_s`）、新组的台站列表 | 两组离散、定位变化的分布、是否建议采用 |
| `expectation_depths.py` | 对没有深度约束的事件改报期望震源 | NonLinLoc 接口的 `events.csv`、约束判据 | 改写后的目录和改动清单 |
| `drop_beyond_network.py` | 标出台站凸包外超过 10 km 的事件，置为 `rejected` | 目录、台站 | 改写后的目录和清单 |
| `check_submission.py`（checker skill） | 交付前自检：文件位置、列、最终报告是否对应提交的文件、每个报警是否有处置和证据 | 输出目录 | 通过或问题列表 |

脚本都写清参数含义和默认值的来源，出错时给出具体信息。

## 6. 规则的写法

每条规则用同一格式，例如：

> **S−P 深度偏差超过门槛。** 适用：`sp_depth_offset` 超过 1.5 km。默认：按报警方向检查速度模型和基准面（近地表太快或太慢、深度基准错）。证据：近台 S−P 深度、深度分布、Wadati 发震时刻，改动前后一起看。不适用或不要做：不要以这个量归零作为采用改动的标准，它只给方向不给校正量；不要用一边倒的台站延迟吸收它。例子：一次运行中报警为目录偏浅 2.7 km，参考目录证实偏浅 1.8 km；把 Vs 缩放到使报警归零后，目录变为偏深 1.2 km。

## 7. 快速评测

现在的开发循环每轮约半天、整条流程跑完才知道效果。按"先建评测"的做法，增加一层决策点评测：

- **场景：** 从已有运行中截取关键决策点，给 Agent 冻结的中间产品、checker 报告和一句任务说明，例如"这是绝对定位的产品和报告，处理报警并给出更新后的目录"。时间预算 30–60 分钟。
- **评分：** 用评分器在同一时间窗上评更新后的产品，看对应判据是否改善且没有新的问题；处置是否给了证据。
- **首批场景（来自两轮开发）：**
  1. 单分量台站的噪声拾取（是否检验后再加入）；
  2. S−P 深度偏浅（是否纠正且不过度）；
  3. 网格边缘的深度堆积（是否改报期望震源）；
  4. 台网外事件（是否剔除）；
  5. 只到绝对定位就要交付（是否做模板匹配和相对重定位）；
  6. 震级单位错误（早期运行中的典型错误，作为回归）。
- **用法：** 每次改 skill 先跑这几个场景（并行，约 1 小时），改善了再跑完整的开发轮次；每次改动和对应的场景结果记一行，相当于 ACE 的增量条目。

## 8. 与实验设计的关系

- **两个 skill 的分工不变：** checker skill 只讲用法和交付；知识 skill 讲流程和判断。S2c（只有 checker）不在主分析里，所以把"每阶段跑 checker"写进知识 skill 不影响主比较（S1 对 S3）。
- **可以增加一个对比：** 同样的知识，写成说明书（1.5）和写成流程（2.0），在开发窗口上各跑一轮。SkillsBench 指出了"全面文档式收益最低"，但没有在同一知识上做这个对比；这对论文是一个直接的贡献点。
- **地震学方向目前没有经过准确性评估的专家 skill 集，** 这部分本身可以作为论文的贡献之一。

## 9. 相关但不在 skill 里的改动

- **checker：** `events_with_few_picks` 不再统计没有拾取的模板匹配检测事件，这类事件另外报告数量，避免反向劝退模板匹配。
- **运行环境说明：** 写明可用的 CPU 数量（Agent 两次把 cgroup 设置误读为只有 1 个 CPU）。这条对所有臂相同。
- **台网外事件：** 已准备的知识改动并入 `stages/03_absolute_location.md` 和 `drop_beyond_network.py`。

## 10. 工作顺序和工作量

1. 第二轮剩下的 Kīlauea、Prague 跑完，评分并写第二轮记录（半天）。
2. 写新的 `SKILL.md` 和 `stages/`，把现有内容按新格式迁移、删减、消除矛盾（一天）。
3. 写四个脚本和单元测试（半天）。
4. 建六个决策点场景和评测脚本（半天到一天）。
5. 跑场景评测，修改，再跑第三轮开发（六个案例，约半天）。
6. 结果稳定后重新冻结，跑正式实验。

## 11. 风险

- **流程写得太死：** 规定的做法不适合某个案例时反而有害（SkillsBench 的主要失败模式）。对策：每条默认做法都写偏离条件，评测场景里包含"应该偏离"的情形。
- **场景评测与完整流程不一致：** 决策点做对了，完整运行中也可能不走到那一步。对策：场景评测只用于筛选改动，采用前仍要跑完整的开发轮次。
- **模型差异：** 前沿结论多来自 Claude、GPT、Gemini；我们用 GLM-5.3，skill 的效果可能不同，只能用自己的评测判断。
- **防泄漏：** 例子和脚本都要过泄漏扫描；例子的数字来自运行记录，不出现案例名和地名。
