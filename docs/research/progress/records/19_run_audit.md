# 运行审计与过程指标（2026-11-08）

问题：每轮开发靠人工翻运行记录分析，太慢；最终判据又被速度模型带来的共有偏差主导，看不出 skill 改变了 Agent 的哪些做法。做法：脚本 [`workflows/development/run_audit/audit_runs.py`](../../../../workflows/development/run_audit/README.md) 自动提取每次运行的关键决策，并给出过程指标（全部运行约一分半钟）。

## 覆盖

44 次已评分的运行：S0 `min` 5 次、S1 `tools` 7 次（按开发窗口重评）、后端三臂各 7 次、S3 `knowledge` 1 次、开发循环 `dev_knowledge` 10 次（第一、二轮）。

## 过程指标与结果的关系

| 过程 | 运行数 | 对应判据不通过的比例 |
|---|---|---|
| 做了相对重定位 | 32 | 偏离构造或水平离散 44 % |
| 没做 | 12 | 67 % |
| 做了模板匹配并并入目录 | 6 | 大事件齐全或大事件后完整性 17 % |
| 没有 | 38 | 39 % |

过程指标能预测结果，而且一次运行就能读出，不受速度模型共有偏差的干扰，比最终判据更适合衡量 skill。

## 各臂的做法

| 臂 | 运行数 | 模板匹配并入 | 相对重定位 | checker 运行次数（中位） | 时长（中位，小时） | 费用（中位，美元） |
|---|---|---|---|---|---|---|
| S0 `min` | 5 | 0 % | 0 % | 0 | 5.5 | 18 |
| S1 `tools`（全量） | 7 | 14 % | 86 % | 0 | 6.2 | 24 |
| 后端三臂（拾取和关联固定） | 21 | 0 % | 100 % | 0–9 | 2.6–4.1 | 17–22 |
| S3 开发循环（1.4、1.5） | 10 | 40 % | 40 % | 8.5 | 5.5 | 23 |

- **知识让模板匹配用得更多**（S3 40 % 对 S1 14 %），但仍有一半以上的 S3 运行没有并入检测：Kaikōura 第二轮、Kīlauea 第一轮跑了模板匹配却没有并入。
- **S3 做相对重定位的比例反而比 S1 低**（40 % 对 86 %）。S3 的 Agent 每次运行 checker 5–15 次，时间花在处理报警上，标准步骤被挤掉：Ridgecrest 两轮、Kīlauea 两轮都没有做。这是 2.0 把流程写成清单、把模板匹配和重定位列为默认步骤的直接理由；第三轮用这两个指标检验。
- **第二轮修复的问题保持住了：** 只有 P 拾取的台站组离散是基准的 0.45–0.63 倍（第一轮 Maple 为 3.3 倍）；Kaikōura 第二轮的深度堆积消失。
- **台网外事件：** Kaikōura 两轮 5–7 %、Kīlauea 两轮 14–29 % 仍在提交的目录里（Kīlauea 的这部分在评估区域之外，不影响评分）；2.0 用脚本剔除。

## 用法

每轮开发结束后先跑审计：过程指标回答"skill 有没有改变做法"（每个案例一次运行即可），最终判据只在过程改变之后再看。
